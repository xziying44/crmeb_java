# 超市演示数据设计

## 背景

当前演示库中的商品分类和商品数据很少，仅有少量酒水相关分类和 1 个商品，无法支撑“超市进货商城”的正式演示。用户要求基于本地素材目录补齐常用超市分类，新增 30-50 个示例商品，并将对应图片上传到当前数据库已配置的腾讯云 COS，再输出可在真实演示环境直接执行的 SQL。

## 目标

1. 在 `eb_category` 中建立可直接用于正式环境的超市常用分类树。
2. 在 `eb_store_product` 及其关联表中新增 30-50 个示例商品。
3. 统一使用本地素材目录中的商品图，上传到当前腾讯云 COS，并同步写入 `eb_system_attachment`。
4. 将本次新增数据整理为 `db_sql/2026-03-09/` 下的可重放 SQL，便于导入真实演示环境。

## 现状与约束

### 数据现状

- 商品分类使用 `eb_category`，产品分类的 `type=1`。
- 商品主表为 `eb_store_product`，详情和规格分别落在 `eb_store_product_description`、`eb_store_product_attr`、`eb_store_product_attr_value`。
- 图片素材表为 `eb_system_attachment`。
- 当前库中商品上传方式配置为腾讯云 COS：
  - `uploadType=4`
  - `txUploadUrl=https://jqy-1256427905.cos.ap-guangzhou.myqcloud.com`
  - `txStorageName=jqy-1256427905`
  - `txStorageRegion=ap-guangzhou`

### 素材约束

- 素材来自 `/Users/xziying/Downloads/超市海报商品图片水果蔬菜图生鲜饮料海鲜零食便利店外卖素材大全`。
- 需要从现有目录中挑选风格统一、适合电商商品卡片展示的图片。
- 现有“饮品酒水/酒类”分类图片需要同步替换为同风格图片。

### 交付约束

- 不做业务代码功能改造，以数据构建和导出为主。
- 不实际提交 git commit；只保留文件变更，并在结束时给出建议的提交信息。
- SQL 需要尽量可重放，避免重复执行产生重复数据。

## 方案选择

### 方案一：只写 SQL

优点：
- 交付简单。

缺点：
- 无法自动完成本地图片上传 COS。
- 手工维护大量图片 URL 和附件记录，容易出错。

### 方案二：本地脚本生成数据并导出 SQL

优点：
- 能串联“挑图、上传、落库、导出 SQL”全流程。
- 便于复用和校验，后续增删商品也更稳。

缺点：
- 需要补充少量脚本与清单文件。

### 方案三：走后台接口批量造数

优点：
- 最贴近业务使用入口。

缺点：
- 依赖服务鉴权与接口状态。
- 批量图片、导出 SQL、重复执行控制都更复杂。

## 最终方案

采用“本地脚本生成数据并导出 SQL”的方案。

实现上分为四步：

1. 扫描本地素材目录，提取分类候选和图片清单。
2. 维护一份超市分类与示例商品映射清单，明确每个分类使用的素材、商品名、价格、库存、规格。
3. 编写本地数据生成脚本：
   - 按清单选择图片；
   - 上传到腾讯云 COS；
   - 生成附件数据、分类数据、商品数据和关联数据；
   - 导出为 `db_sql/2026-03-09/` 下的 SQL。
4. 在本地 Docker MySQL 中执行并校验，确认前后台可展示后保留最终 SQL。

## 分类设计

- 早餐烘焙

## 商品设计

- 商品数量控制在 30-50 个。
- 每个一级分类安排 2-5 个代表商品。
- 商品优先使用单规格，少量饮料/粮油类保留双规格示例。
- 商品字段至少补齐：
  - `store_name`
  - `store_info`
  - `keyword`
  - `cate_id`
  - `price/cost/ot_price`
  - `unit_name`
  - `stock`
  - `image/slider_image`
  - `is_show/is_best/is_new/is_hot`
- 商品详情描述保持简洁，以便前台详情正常展示。

## 图片与附件设计

- 每个分类配置 1 张分类图。
- 每个商品至少配置 1 张主图，优先配置 2-3 张轮播图。
- COS 对象键沿用现有格式：`crmebimage/public/product/YYYY/MM/DD/<随机文件名>.<后缀>`。
- 每张上传图片都同步落 `eb_system_attachment`，`image_type=4`，保证后台素材库一致。

## SQL 设计

在 `db_sql/2026-03-09/` 下产出：

1. 数据清单文件：记录分类、商品、本地图片路径、COS 对象键、价格库存等元数据。
2. 最终导入 SQL：按顺序处理分类、附件、商品、规格、详情。
3. 使用说明：说明执行顺序和影响范围。

SQL 采用“按本次数据名称集清理后重建”的方式，确保可重复执行：

- 先删除本次新增的商品关联数据。
- 再删除本次新增的商品。
- 再删除本次新增的分类。
- 最后插入新分类、附件、商品和关联表数据。

## 验证策略

1. 校验图片已成功上传到 COS，且可通过 `txUploadUrl` 访问。
2. 校验本地数据库新增分类总数、层级关系和路径正确。
3. 校验商品数量、分类归属、图片字段、规格字段完整。
4. 校验 SQL 在本地数据库重复执行不会产生重复数据。
5. 抽查前台/后台页面，确认列表、详情和图片显示正常。

## 风险与处理

### 素材命名不统一

通过人工维护映射清单收敛，不直接依赖目录名自动生成最终商品名。

### 正式环境存在同名分类或商品

SQL 只针对本次约定名称集清理，避免误删无关数据；如正式环境已有同名核心业务数据，需要导入前先确认。

### 图片上传失败

脚本需要在上传时输出失败明细并中断，不允许生成不完整 SQL。

### 自增 ID 不一致

导出 SQL 时不依赖本地偶然 ID，尽量通过名称定位或显式重建顺序保证可执行性。
